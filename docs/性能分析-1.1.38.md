# 性能分析（基线 1.1.38）

> **2026-10-24 更新**：P0-2（主界面每帧剔除）和 P1-1（RichText active 抖动）已在 1.1.39 落地，
> 实测结果见文末「六、1.1.39 实测」。P0-1（立绘图集）尚未实施，原因见该节。

本轮**没有改任何游戏代码**，只做测量和定位。所有数字都是在雷电模拟器 9（index 0，Android 9，
x86 上跑 ARM 转译）上实测的，命令都写在文末，可复现。

---

## 一、实测结论（先看这个）

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| 前台静止 CPU | **144 %**（1.44 个核） | `top -p <pid>`，主界面不动、无操作 |
| 帧间隔 平均 | **18.1 ms ≈ 55 fps** | `dumpsys SurfaceFlinger --latency`，127 帧 |
| 帧间隔 p50 / p90 / p99 | 17.0 / 23.8 / 44.6 ms | 60 Hz 屏幕的预算是 16.7 ms |
| 超过 20 ms 的帧 | **24 %**（30/126） | 这就是"看着卡一下"的来源 |
| 拖动地图时 | 17.6 ms、p90 23.8 ms、25 % 超 20 ms | 和静止几乎一样 ⇒ 不是滚动算法的问题 |
| 切后台 | **0 %** | Cocos 暂停正常，不白烧电 |
| 冷启动 | 3.46 s 出 Activity，4.06 s 出场景，5.39 s 进入游戏 | `am start -W` + DSHBOOT 日志 |
| 常驻内存 | 540 MB RES | 模拟器数值，手机不可直接比 |

一句话：**游戏没有真正的"空闲帧"**，每帧都在 16.7 ms 预算线上下波动，四分之一帧超时，
所以体感是"不算卡但一直不跟手"。优化空间在里面，不在渲染画质。

> 注意：雷电是 ARM 转译，绝对 CPU 值偏大（大概 2~3 倍）。手机上大概是 40~60 % 一个核，
> 但"卡在预算线上"的比例是一样的，中低端机会明显更差。

## 二、每帧到底在干什么（代码定位）

### 1. `VHBgshiMap.update()` —— 主界面每帧遍历所有部门图标

`源码/index.pretty.js` 137957–137972（对应 `VHBgshiMap.ts`）：

```js
update(t) {
  let i = this.fatherIcon.position;
  this.txtIcon.setPosition(i); this.txtIconP.setPosition(i); this.node_qipao.setPosition(i);
  for (const t in this.iconObjs) {          // 办公室树上的每个部门/秘书/董事
    let i = this.iconObjs[t];
    if (1 == i.active) {
      t = i.isp ? this.zgNodegzt("touxiang", i) : this.zgNodegzt("icon1/touxiang", i);  // 字符串拼 key
      var e = i.getComponent(r).contentSize;
      let o = i.worldPosition, n = i.worldScale,
          h = new s(o.x, o.y, e.width * n.x, e.height * n.x).intersects(this.rect);     // 每帧新建 Rect
      t.active = h
    }
  }
}
```

问题：
- **每帧 O(图标数)**。`combm` 里有 73 个对象，树上的图标几十个，就是几十次循环 × 每帧。
- 每个图标每帧做 2 次 `"ANode:" + path` 字符串拼接 + 2 次 `getComponent` + **`new Rect` 一次**。
  按 40 个图标算，**每秒 2400 次字符串分配 + 2400 个 Rect 垃圾**，全是 minor GC 的料。
  p99 44.6 ms 的尖峰和这个量级的分配很吻合。
- 它做的工作只是"把名字标签在离开可视区时隐藏"，而这个结果只在 **拖动/缩放/切人** 时才变。

### 2. 时钟节点的 0.01 s 调度 —— 理论上 100 Hz，实际每帧一次

`index.pretty.js` 150712–150717：

```js
checkDingshi() {
  let e = this.zgNodegzt("timeLay1"), i = c.base.sec;
  ...
  this.gsScheduleStnode(e, (() => { ... i-- ... this.timeLast() ... }), .01)   // ← 0.01 秒
}
```

`gsScheduleStnode`（154288）内部就是 `node.schedule(fn, 0.01)`。0.01 s 小于帧间隔，
等于**每帧最多跑一次**；回调本身不重，但它意味着"游戏秒"是按帧推的，且常驻一个
每帧闭包调用。

### 3. 0.1 s 的成就检查 —— 每秒 10 次要扫一遍窗口列表

`index.pretty.js` 150710 挂的 `checkCjInfo`（150751）→ `checkOpenCjWin`（150768）：

```js
checkOpenCjWin() {
  if (!h.getNewOpen(100001) || c.cjInfo.zhibo.length <= 0) return;
  ...
  let e = n("Canvas/window").children;
  for (let i of e) if (1 == i.active) return;    // 遍历窗口根的所有子节点
}
```

`checkCjInfo` 本身在没变化时很便宜（`cjCheckType` 全 null 直接跳过），但它**每 0.1 s 必定
调一次** `checkOpenCjWin`，后者的 `getNewOpen` + `Canvas/window` 子节点遍历是实打实的开销。
`n(path)` 是 `find()`，没走缓存的话要按名字逐层找。

### 4. 每个部门立绘一张独立贴图 —— 直接打散合批

`源码/modules/03_widgets/ZGGSOfficeFx.ts`：`__depIconGet(name)`（第 56 行起）
对 55 张立绘**每张 `new Texture2D()` + `uploadData()`**，再由 `gsSprHtsst1`（299 行）
设到各自的 `touxiang` 上。

后果：Cocos 的合批粒度是 (材质 + 贴图)。**55 张独立贴图 = 屏幕上每个部门图标都是独立
draw call + 独立纹理绑定**，同一个办公室界面 10~40 个图标就是 10~40 个 draw call，
在 ARM 转译 / 中低端 GPU 上这是最贵的一项。而它们本来可以塞进一张 680×560 的图集里。

### 5. `gsRichLbltxtgrs` 每次调用都把节点 active 关了再开

`index.pretty.js` 154222–154225：

```js
gsRichLbltxtgrs(t, s, e = null) {
  var n = this.zgRichStrgrst(t, e);
  n ? (n.node.active = !0, n.string = s, n.node.active = !1, n.node.active = !0) : ...
}
```

`active = false → true` 会让 Cocos **整棵子树走一遍停用/启用**（组件 onDisable/onEnable、
从渲染场景移除再加回、批处理列表重建）。它每次只是为了一次 RichText 重新排版。
加载页、弹窗标题、跑马灯都用它，属于"每次调用都在抖一下"的类型。

### 6. 加载页是"每帧一次"的推进器

`index.pretty.js` 136140：`this.schedule(p, 0)` —— interval 0 就是每帧。里面每帧都
`zgSpriteFargst` + `gsTxtLblgs`（进度条 + 百分比）。只影响启动那几秒，不是常驻问题，
但改成 0.05 s 且数值没变就不写，能省下启动期的无谓 label 重排。

## 三、优化清单（按性价比排序，均未实施）

### P0-1 立绘合并成一张图集（预期最大收益）

- 改法：把 55 张 85×80 的 RGBA 拼成一张 **680×560**（8 列 × 7 行）的 `Texture2D`，
  每张生成一个 `SpriteFrame`，`rect` 指向图集里的偏移；`__depIconGet(name)` 改成查表返回
  `SpriteFrame`，`__depIconB64` 只保留一张大图。
- 收益：办公室界面 draw call 从"每图标 1 个"降到 **1 个**（同一张图集可合批），
  连带省掉几十次 `glBindTexture`。
- 风险：**低**。视觉完全一致；只需注意 `setFilters` 与边缘留 1~2 px 空隙防串色。
- 代价：`ZGGSOfficeFx.ts` 里那张 2 MB 的表要重排成一张图，构建脚本里加一步拼接。

### P0-2 把主界面每帧的图标剔除改成"脏了就更新 + 限频"

- 改法：在 `VHBgshiMap` 里缓存上一次的 `fatherIcon.position` / `scaleNode.scale` / 图标集合；
  `update()` 里先比对，没变就 `return`；再叠一层 10 Hz 限频（`this._t += dt; if (this._t < 0.1) return;`）。
- 收益：省掉每秒 2400 次字符串拼接 + 2400 个 `new Rect`，GC 尖峰（p99 44.6 ms）应该明显收敛。
- 风险：**低**。拖动时依然每帧判定（位置变了就进分支），只是静止时不再空转。

### P0-3 降低两个常驻定时器的频率

- `checkDingshi`：`.01` → `.1`（回调里有 `i--` 计数，改频率要同步把步长从 1 改成 0.1 或者
  把 `c.base.sec` 放大 10 倍，**这一条要连带核对游戏内时间流速**，风险中等）。
- `checkCjInfo`：`.1` → `.3`，并在 `checkOpenCjWin` 开头加"没有新成就就直接 return"，
  避免每秒 10 次扫 `Canvas/window.children`。
- 收益：合计约 3~5 % 的常驻 CPU。
- 风险：中（时间流速那条必须实测一天游戏内时间对得上）。

### P1-1 干掉 `gsRichLbltxtgrs` 里的 active 开关

- 改法：直接 `n.string = s;`。如果当初是为了让 RichText 重算，用 `n.markForUpdateRenderData(true)` 代替。
- 收益：每次调用省一次子树停用/启用；加载页和弹窗肉眼可见地"顺"一点。
- 风险：低（要回归一遍带富文本的界面：公告、跑马灯、招人弹窗）。

### P1-2 加载页推进器降频

- `this.schedule(p, 0)` → `.05`，并且 `fillRange` / 百分比字符串没变就不写。
- 收益：启动期 CPU 峰值下降，启动时间基本不变（瓶颈是解密 + 解析 4.6 MB jsc）。
- 风险：极低。

### P2 备选（先不动）

- `game.frameRate = 45`（菜单/纯文字界面）：能省 25 % 上下，但动画会变钝，需用户拍板。
- `Label.cacheMode = CHAR`：静态文字多的界面收益大，但 Cocos 3.6 里字符模式下字号/描边
  组合会爆图集，本项目描边标签多，**不建议**盲目开。
- 启动期把 `__depIconB64`（1.5 MB base64 常量）从 `index.jsc` 里挪到外部 bin 资源，
  可让 JS 解析体量少 1.5 MB（启动少几十到一百毫秒），但会动到资源加载链，风险中。

## 四、建议的落地顺序

1. **P0-1 图集**（收益最大、风险最低，改的是我们自己加的模块，不碰原版逻辑）
2. **P0-2 脏检查 + 10 Hz**（纯 JS，改 `VHBgshiMap`，行为不变）
3. **P1-1 / P1-2**（顺手就做，一起回归）
4. **P0-3 定时器**（要单独验证游戏内时间流速，放最后，单独出一版）

每做完一项都按同一套指标对比：**144 % CPU → 下到多少**、**p90 23.8 ms → 下到多少**、
**>20 ms 的帧占比 24 % → 下到多少**。达不到就不收。

## 五、复现命令

```powershell
$adb="C:\Program Files (x86)\Android\android-sdk\platform-tools\adb.exe"
$d=@("-s","127.0.0.1:5555")
& $adb @d shell am start -W -n com.sky.dsz.dsh/com.cocos.game.AppActivity     # 冷启动
$pid_= & $adb @d shell pidof com.sky.dsz.dsh
& $adb @d shell "top -b -n 3 -d 2 -p $pid_"                                   # 前台 CPU
& $adb @d shell "top -H -b -n 1 -p $pid_"                                     # 线程级
$dev="SurfaceView - com.sky.dsz.dsh/com.cocos.game.AppActivity#0"
& $adb @d shell "dumpsys SurfaceFlinger --latency '$dev'"                     # 帧间隔（ns）
& $adb @d shell input keyevent KEYCODE_HOME                                   # 切后台应降到 0 %
```

帧间隔那份数据第一行是刷新周期（16666666 ns），之后每行三列是
`desiredPresent / actualPresent / frameReady`，用第二列相邻差值算帧间隔。

## 六、1.1.39 实测（P0-2 + P1-1 落地后）

### 改了什么

| 文件 | 改动 |
| --- | --- |
| `源码/modules/00_core/VHBgshiMap.ts` | `update(dt)` 增加脏检查：`fatherIcon.position` / `scaleNode.scale` 没变时，图标剔除循环降到 4 次/秒兜底；拖动时（位置变了）仍然逐帧判定，视觉无差别 |
| `源码/modules/03_widgets/ZGGSOfficeFx.ts` | `gsRichLbltxtgrs` 去掉 `node.active = !1 → !0` 的来回抖，只保留 `active = !0` + `string = s` |

### 同一状态、前后紧挨着测（1.1.38 → 1.1.39）

| 指标 | 1.1.38 | 1.1.39 | 变化 |
| --- | --- | --- | --- |
| 前台 CPU | 144 % | **92 %** | **−36 %** |
| 帧间隔平均 | 18.11 ms | **16.92 ms** | −6.6 %（55.2 → **59.1 fps**） |
| p50 | 16.98 ms | 16.36 ms | −0.62 ms |
| p90 | 23.84 ms | **21.58 ms** | −2.26 ms |
| p99 | 44.61 ms | **32.16 ms** | **−12.45 ms** |
| >20 ms 的帧 | 24 %（30/126） | **16 %（20/126）** | −8 个点 |
| 拖动时 p90 | 23.76 ms | 22.14 ms | −1.62 ms |
| 拖动时 >20 ms | 25 %（32/126） | **17 %（21/126）** | −8 个点 |

p99 从 44.6 ms 掉到 32.2 ms 最明显，这正是「每帧 new Rect + 字符串拼 key」造成的
GC/长帧尖峰被削掉的证据。

### 测量口径的坑（必须写下来）

CPU 的绝对值**跟游戏内状态强相关**：同一个 1.1.39，在「有存档、停在办公室」状态下
测到 92 %，在「刚 `pm clear`、新手引导期」状态下测到 140~150 %，来回浮动 ±30 个点。
所以：

- **CPU 只做方向性对比**，必须同状态、背靠背测，且用 10 s 窗口平均（`top -n 1` 单次采样会骗人）。
- **帧间隔（p90 / p99 / >20 ms 占比）才是稳定指标**，跨状态波动小，验收以它为准。
- 不要用 `adb install -r -d` 降级装旧包：本项目 `android:debuggable` 为 false，
  降级会被 `INSTALL_FAILED_VERSION_DOWNGRADE` 拦下，要做 A/B 只能 `pm clear` + 全新装。

### P0-1（立绘图集）为什么还没做

不是做不了，是**有一个必须先验的未知数**：55 张立绘现在是「一人一张 85×80 贴图」，
改成一张图集就得给每个 `SpriteFrame` 设 `rect` 子矩形，而 `rect.y` 到底是从纹理顶部还是
底部算起，在这个 Cocos 3.6.3 构建里无法从代码断定（`_calculateUV` 的数学和
`UNPACK_FLIP_Y_WEBGL=false` 的 GL 后端结论互相耦合，全矩形时两者等价，看不出来）。
一旦猜错，55 张立绘会上下颠倒——这是肉眼可见的事故，不能靠猜。

正确做法是先出一个**探针包**（在场景中央画一个 4 行纯色块：红/绿/蓝/白，走同一个
`uploadData` + 全矩形路径），截图读像素确定行序，再按正确映射做图集。
探针包 + 图集包 = 两次构建，留到下一轮单独做。
